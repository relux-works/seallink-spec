## 1. Universal Grant Model (`seallink-grant/1`)

A `seallink-grant/1` (`<= 65536` bytes, `schemas/grant.schema.json`) is the universal authorization instrument across people, organizations, services, and agents (`SL-GRNT-001`, `decided`). Every grant carries **exactly one** of `issuer` (root grant) or `parent` (depth-2 child grant).

### 1.1 Unilateral Base and Optional Contract Binding

- **Unilateral base:** An autonomous root grant requires ONLY the issuer's valid `SignatureSet` matching `issuer.role_policy` (pinned on chain in `link.grant` per `SL-IDEN-003`). A root grant issued on behalf of a `ward` omits `issuer.role_policy`, sets `payload.guardian_context`, and carries top-level `guardian_approvals[]` satisfying `required(derived_event_class)` (`SL-WIRE-013`, `SL-ORIG-006`). Neither form requires recipient assent or imposes obligations on the recipient.
- **Contract-bound grants:** Setting optional `contract_id` binds the grant to a `seallink-contract/1` (`SPEC-05`): the grant's window MUST nest inside the contract (and any framework contract), all `machine_clause_indices` MUST be disclosed and match the grant's capabilities, and spending the contract or framework seal terminates the grant (`SEAL_SPENT`). Action profiles with `requires_contract = true` refuse unilateral grants (`GRANT_CONTRACT_REQUIRED`).

### 1.2 Recipient Modes (`SL-GRNT-002`, `decided`)

Every grant selects **exactly one** recipient mode:
1. **By Key (`mode = "key"`):** Names one `xonly_64hex` public key (suitable for ephemeral key-only workers and hardware keys). Ledger name resolution is skipped for the recipient.
2. **By Name (`mode = "name"`):** Names `(name, registration, owner_policy)`. At invocation, the verifier resolves `name`, confirms its active registration equals `registration`, confirms its current live output matches `owner_policy` with writer-verified history (`NAME_OWNER_MISMATCH`), and accepts signatures from the name's current authorized `nostr`/request key, permitting same-owner key rotation and name renewal without reissuing the grant while preventing an expired-name re-registrant from inheriting prior grants.
3. **By Group (`mode = "group"`):** Names a `ThresholdPolicy` (`m-of-n` distinct keys), authorizing execution ONLY when `>= m` distinct co-recipients sign `seallink-invocation/1` (`SignatureSet`).

### 1.3 Concrete `executor` vs. Stateless `executor_ref` (`SL-GRNT-003`, `decided`)

Every action leaf in a service profile declares four orthogonal boolean properties (`SPEC-07 §4.1`): `external_mutation`, `discloses_data`, `quota_consuming`, and `allows_executor_ref`. Every grant carries **exactly one** of:
- **Concrete `executor: {name, key}`:** Pins one specific service identity and receipt key. **MANDATORY** whenever ANY capability in `capabilities[]` has `external_mutation = true`, `quota_consuming = true`, carries `quotas`, uses `single_use` revocation, or includes `delegate`. *(Concrete `executor` does NOT waive holder provider binding on `mailbox:` targets — the executor MUST still verify the holder's confirmed `seallink-manifest/1` pins this provider's exact `NamePin` for `("mail", <label>)`, refusing `SERVICE_PROVIDER_UNBOUND` if missing or mismatched.)*
- **Dynamic `executor_ref: {provider_of, service_type, label}`:** Requires `executor_ref.provider_of == root_grant.issuer.name` (`GRANT_TARGET_UNAUTHORIZED` otherwise) and resolves at verification time against `provider_of`'s current confirmed `seallink-manifest/1` `providers[]` entry (`NamePin` + service manifest `receipt_key`) matching `(service_type, label)`. **STRICTLY FORBIDDEN** if the grant carries any `quotas`, uses `single_use` revocation, includes `delegate`, or includes any action with `external_mutation = true` or `allows_executor_ref = false` (`GRANT_EXECUTOR_REF_FORBIDDEN`).

> **Rationale:** Stateless data-read actions (e.g., `mail/read` without quotas) have `discloses_data = true` and `external_mutation = false`, so resolving the current pinned provider via `executor_ref` cannot double-spend quotas or cause duplicate side effects.

### 1.4 Validity Window and Revocation Modes (`SL-GRNT-004`, `decided`)

- **Half-open block window:** `[not_before_height, not_after_height)` with `recent_block_height <= not_before_height < not_after_height` and `not_after_height <= issuer_name_expiry_at_issuance` for sealed grants (verifiers MUST check `not_after_height <= issuer_name_expiry_at_issuance` and refuse `GRANT_WINDOW_CLOSED` if exceeded). Admission at `tip == not_after_height` refuses `GRANT_WINDOW_CLOSED`. Optional `min_depth` (`1..144`, defaults to `1`) specifies the issuer's minimum required anchor/seal confirmation depth.
- **Exact `seallink-issuance/1` Anchor Commitment Preimage:** Every sealed grant commits on chain to `typed_digest(seallink-issuance/1)` = `H_tag("seallink-issuance/1", canonical_JCS(IssuancePrep))`, where `IssuancePrep` (`schemas/grant.schema.json#/$defs/IssuancePrep`) carries:
  - `type`: `"seallink-issuance/1"`
  - `genesis`: `grant.payload.genesis`
  - `grant_id`: `id(seallink-grant/1)`
  - `grant_content_addr`: `content_addr(seallink-grant/1)`
  - `contract_id`: `grant.payload.contract_id` *(present strictly if and only if the grant carries `contract_id`; omitted otherwise)*.
- **Two revocation modes:**
  1. **`revocation.mode = "seal"` (Standard Default):** Names `construction ("W" | "L")`, `kind ("revocable" | "single_use")`, and confirmed `seal: {txid, vout, script_policy}`. Root grants are anchored via `OP_RETURN 0x01` OR Merkle batch `0x02` (with `MerkleProof` and per-leaf linkage output `(seal_txid, seal_vout + 1)` spent by the `0x02` transaction); **depth-2 child grants MUST use individual `OP_RETURN 0x01` (never `0x02`)** (`CHAIN_FRAME_INVALID`). Spending a `revocable` seal closes the grant at mempool speed (`SEAL_SPENT`). A `single_use` seal MUST use `ScriptPolicy` template `single_use_1_of_2` and follows the branch-aware state machine in `SPEC-02 §6.2`.
  2. **`revocation.mode = "window_only"` (Root-Only Zero-Tx Ephemeral Mode):** Strictly permitted ONLY on **root** grants without `delegate` (`parent` and `delegate` MUST be absent), with `not_after_height - not_before_height <= 12` blocks. Requires zero ledger transactions. **Executors MUST refuse `window_only` by default (`GRANT_SEAL_REQUIRED`)** unless local executor policy explicitly opts in for that action and budget tier. Emergency rotation/removal of the issuer's `link.grant` (`NAME_ROLE_CHANGED`) still terminates all live `window_only` grants immediately.

### 1.5 Text-vs-Effect Invariant (`SL-GRNT-005`, `decided`)

A grant MAY carry optional `terms_text` solely to guide cognitive work (e.g., `agent/brief`). Any mechanical effect executor (`mail/*`, `agent/tool`, `agent/session`, wallets, locks, name updaters, blob stores) **MUST** refuse any grant containing `terms_text` (`GRANT_TEXT_FORBIDDEN`).

## 2. Invocations (`seallink-invocation/1`) and Signed Receipts (`seallink-receipt/1`)

### 2.1 Signed Invocation and Acyclic Single-Use Delivery (`SL-GRNT-006`, `decided`)

Every execution request is a canonical JCS `seallink-invocation/1` (`<= 1 MiB`) signed by the final grant's recipient (`SignatureSet`):

- Binds `network`, `genesis`, concrete `executor {name, key}`, exact `action`, `target`, closed typed `arguments` (validated against the owning profile schema), optional `content_salt` (`SPEC-05 §3`), `proof_path` (1 entry for root grant, 2 entries `[parent, child]` for delegated child grant, each optionally carrying `issuance_txid` and `batch_proof`), 32-byte CSPRNG `nonce`, and wall-clock half-open window `[iat, exp)` (`iat <= now < exp`, no grace, `INVOKE_TIME_INVALID`).
- **Acyclic single-use consumption (`0x11`):** `seallink-invocation/1` NEVER embeds `use_txid`. For a `single_use` grant:
  1. The grantee constructs and signs `seallink-invocation/1`, computing `invocation_content_addr = SHA256(canonical_JCS(invocation))`.
  2. The grantee broadcasts `T_use` spending the `single_use_1_of_2` seal via branch `0` (`grantee`, `SIGHASH_ALL`) with `OP_RETURN 0x11` (`SINGLE_USE_CONSUMPTION`) committing `invocation_content_addr`.
  3. The grantee delivers `(seallink-invocation/1, use_txid = txid(T_use))` in the transport envelope alongside inline grant/contract/manifest bytes. The executor verifies `T_use` on its own chain view (`SPEC-02 §6.2`).
- **Signed arguments are sole authority & clean-room presentation bundle (`D14-M01`):** The executor MUST derive effect parameters strictly from `payload.arguments` (never from transport headers or unsigned wrapper fields) and evaluate every `where` predicate (`SL-WIRE-016`) against `payload.arguments` (`INVOKE_CONSTRAINT_FAILED`). Transport delivery of an invocation pairs `seallink-invocation/1` with an untrusted presentation bundle carrying the referenced off-chain objects (`grants[]`, optional `contracts[]`, `assents[]`, `assent_anchors`, `disclosed_clauses`, `manifests`, `origin_bundle` / `origin_bundles_by_oid`, `notary_acts`, `use_txid`, and `ChainView` snapshots where `ChainViewTx.outputs` includes every relevant transaction output); every presented object is cryptographically verified against local ledger state and never trusted by presentation alone.

### 2.2 Two-Phase Atomic Admission, Quota Accounting, and Late Receipt Settlement (`SL-GRNT-007`, `decided`)

1. **Phase 1 — Atomic Admission & Reserve (`admit_and_reserve`):** Before executing any effect, the executor runs the full 12-step admission pipeline (`§4`, including `pre_effect_recheck`), verifies that every required profile quota (`registry/actions.json` `required_quotas`) is present on the matched capability with exact `resource == target` (when `resource = "{target}"`, else `QUOTA_EXCEEDED`), computes the profile-defined maximum debit for every quota key consumed by the action (`registry/constraints.json`, exact integer/rational arithmetic, never binary64), verifies every quota across **both** accounts for a delegated child grant — the child grant's `own` account keyed by `(account="own", grant_id=child_grant_id, quota_kind, resource, unit, window, bucket_id)` **and** the parent's per-row `row` account keyed by `(account="row", grant_id=parent_grant_id, row_ordinal=child.parent.ordinal, quota_kind, resource, unit, window, bucket_id)` (bounded by the group template row ceiling — strictly isolated per `row_ordinal` so sibling rows sharing one executor never collide, and never charging the parent's `own` account) — plus operator ceilings (`QUOTA_EXCEEDED`), and appends **ONE single atomic `reservation` journal entry** binding `(invocation_id, grant_id, action, nonce, expires_at, recorded_at, reservations[])` — with `reservations[]` emitted in **canonical signed `capability.quotas[]` order, `own` immediately before `row` for each quota** (and `reservations = []` for quota-free invocations), plus `single_use: true, use_txid` (auto-derived from the verified branch-0 `spent_by_txid` on chain when not supplied in the transport envelope) whenever the backing grant uses `revocation.kind = "single_use"` so post-crash `commit_result` recovery is 100% self-contained from `JournalEntry[]` + external witness + `receipt_env` without external side-tables — advancing the external CAS witness by `+1`. If ANY check or quota in the batch fails, the entire reservation aborts leaving all balances and the journal unchanged. A zero ceiling authorizes nothing; missing required profile quota or mismatched quota `resource` refuses (`QUOTA_EXCEEDED`).
2. **Window modes and canonical `bucket_id` grammar:**
   - `term`: `bucket_id = "term"` — cumulative across `[not_before_height, not_after_height)`.
   - `blocks:<N>`: `bucket_id = "blk:" || decimal(anchor_h + floor((tip_height - anchor_h) / N) * N)` — half-open block buckets `[anchor_h + k*N, anchor_h + (k+1)*N)`, where `anchor_h = grant.not_before_height` for `own` accounts and **`anchor_h = parent.not_before_height`** for `row` accounts (preventing a child from shifting row-account block buckets by picking a later `child.not_before_height`).
   - `seconds:<S>`: `bucket_id = "sec:" || decimal(floor(now / S) * S)` — UTC epoch-aligned buckets `[floor(now/S)*S, (floor(now/S)+1)*S)` guarded by a durable per-key monotonic clock watermark (`QUOTA_CLOCK_REGRESSION`).
3. **Phase 2 — Late Receipt Persistence, Strict 1-to-1 Reconciliation & Single Atomic Terminal (`commit_result`):** Real services do not know `result_sha256` until after executing the external effect. Once the effect completes (or produces a final `refused`/`uncertain` outcome) and the executor signs the real `seallink-receipt/1` (`receipt_env`):
   - **Require existing reservation & idempotency (`executed`, `refused`, and `uncertain`):** Confirm a Phase-1 `reservation` exists for `invocation_id` (refuse `INVOKE_REPLAY` if no reservation exists). If `invocation_id` is already terminally settled (`executed` or `refused`): when `content_addr(receipt_env)` equals the recorded `receipt_sha256` (and the stored receipt matches), return `ADMIT` idempotently with **zero** journal writes and unchanged head; when `content_addr(receipt_env)` differs from the recorded `receipt_sha256`, refuse **`INVOKE_REPLAY`** (never overwrite or double-settle). If `invocation_id` previously recorded an `outcome = "uncertain"` receipt `u_sha`: repeating the exact same signed `uncertain` receipt (`content_addr(receipt_env) == u_sha`) MUST return `ADMIT` idempotently with **zero** journal writes and unchanged head; submitting a *different* `uncertain` receipt (`content_addr(receipt_env) != u_sha`) MUST refuse **`INVOKE_REPLAY`**; re-invoking `admit_and_reserve` with the same `invocation_id` while `uncertain` MUST continue returning **`UNCERTAIN`** (an `uncertain` settlement NEVER populates the terminal cached-receipt index); submitting a later valid `executed` or `refused` receipt reconciles and closes the unsettled reservation (charging `settled`, releasing unused reserve, and marking `invocation_id` terminal).
   - **Signed-receipt verification, deterministic `settlements[]` order & exact refusal precedence:** Verify `receipt_env` wire format (`SPEC-01 §7`), exact signature against pinned `executor.key`, and exact payload pin equality (`network`, `genesis`, `executor_name`, `grant_id`, `invocation_id`, `action == reservation.action`, and valid 64-hex `use_txid` on `single_use` — `action`, `single_use`, and `use_txid` are derived strictly from the durable Phase-1 `reservation`, never from caller overrides). Reconcile **`receipt.payload.settlements[]` strictly 1-to-1** against the durable Phase-1 `reservation.reservations[]` lines in three strict passes:
     - **Pass 0 (Structural 1-to-1 key pairing -> `WIRE_MEMBER`):** Verify exact line count equality (`len(receipt.settlements) == len(reservation.reservations)`) and 1-to-1 pairing of every `(account, row_ordinal, kind, resource, unit, window)` key with zero missing, unknown, or duplicate lines (`WIRE_MEMBER`);
     - **Pass 1 (Global `QUOTA_EXCEEDED` across ALL paired lines):** Refuse `QUOTA_EXCEEDED` if ANY paired line has `receipt.settled > reservation.reserved`, OR if ANY entry in optional auxiliary `actual_quota_usage` matching a reserved quota key is `< 0` or `> reservation.reserved` (checked globally BEFORE Pass 2 so an overrun on line `i` always beats an in-range meter or arithmetic mismatch on line `j < i`);
     - **Pass 2 (Arithmetic & meter conservation -> `WIRE_MEMBER`):** Refuse `WIRE_MEMBER` if `actual_quota_usage` contains any extra key absent from the reservation, `receipt.reserved != reservation.reserved`, `receipt.settled + receipt.released != receipt.reserved`, `outcome == "uncertain"` with `released != 0` (also rejected during journal replay as `JOURNAL_LOST`), any in-range `actual_quota_usage[qkey]` differs from `receipt.settled`, or `own.settled != row.settled` for the same quota on a delegated grant.
     The appended journal `settlement` entry's `settlements[]` array **MUST preserve the exact element order of the verified signed `receipt.payload.settlements[]`** and set `settlement.recorded_at = receipt.payload.recorded_at` (guaranteeing byte-identical `JournalEntry` hashes across implementations even when the signed receipt orders lines differently from Phase-1 `reservations[]`).
   - **Receipt-first persistence:** Durably persist the verified signed receipt bytes into the content-addressed receipt store keyed by `receipt_sha256 = content_addr(receipt_env)` **BEFORE** appending the journal entry. Executors MUST NEVER synthesize a fallback hash (such as `SHA256(invocation_id)`) in place of the real `content_addr(receipt_env)`.
   - **Single atomic terminal `settlement` entry (`+1` witness advance):** Append **ONE single atomic `settlement` journal entry** for BOTH ordinary AND `single_use` invocations recording `(invocation_id, grant_id, outcome, receipt_sha256, recorded_at, settlements[])` (with `settlements = []` for quota-free invocations), charging the reconciled `settled` debit and releasing `released = reserved - settled` (for `outcome = "uncertain"`, the full reserve is retained and `invocation_id` remains unsettled for later reconciliation). For `single_use` invocations, `single_use_consumed: true`, `use_txid`, and `closes_grant_id: grant_id` are recorded **at most once** (on the first `settlement` entry for that `invocation_id`, never duplicated if an `uncertain` settlement later reconciles to `executed`/`refused`), atomically updating derived single-use consumption and grant closure state with a single `+1` witness advance!
4. **Uncertain outcomes and crash recovery:** If an executor crashes after Phase 1 (`reservation` committed) and before Phase 2 (`settlement` committed), or if an external effect outcome is uncertain (timeout, network split), the full reservation MUST be retained until operator/protocol reconciliation; replay MUST return `outcome = "uncertain"` and MUST NOT refund or allow a second execution.
5. **Idempotency and Replay:** Request identity is `invocation_id = SHA256(canonical_JCS(invocation.payload))` (excluding `signatures`). A repeated identical `invocation_id` MUST perform zero second effect: if a terminal `settlement` (or `single-use-consumed`) entry exists and the verified receipt blob matching `receipt_sha256` is present in the receipt store, return that stored signed receipt (or refuse `INVOKE_REPLAY` if profile forbids cached return); if the terminal entry exists but the receipt blob is missing or corrupted, MUST refuse **`INVOKE_REPLAY`** (NEVER re-execute!). A reused `nonce` with a different payload MUST refuse `INVOKE_REPLAY`.

### 2.3 Signed Receipt (`SL-GRNT-008`, `decided`)

Every executor answers with a `seallink-receipt/1` (`<= 65536` bytes, `schemas/invocation.schema.json`) signed by its pinned `receipt` key (`executor.key`), recording `invocation_id`, `grant_id`, `action`, `outcome ("executed" | "refused" | "uncertain")`, optional `refusal_code`, `settlements[]`, optional `result_sha256`, and observation `(tip_height, tip_hash, recorded_at)`. Each entry in `settlements[]` (`maxItems: 64`, supporting full lossless reporting of up to 32 capability quotas across both `own` and `row` accounts within the 64 KiB envelope ceiling) MUST specify `account ("own" | "row" | "session")`, `row_ordinal` (REQUIRED iff `account = "row"`, FORBIDDEN otherwise), `kind`, `resource`, `unit`, `window`, `reserved`, `settled`, and `released`. Callers MUST verify receipts solely against their pinned `executor.key`.

## 3. Bounded Depth-2 Re-Delegation

A root `seallink-grant/1` MAY authorize bounded child grants by including `delegate` (`SL-GRNT-009`, `decided`). Maximum authority path depth is **2** (root -> child; children MUST NOT carry `delegate` and MUST use `revocation.mode = "seal"` bound to `delegate.child_seal_key`, `GRANT_NOT_DELEGABLE`).

1. **Separated delegation and child-seal keys:**
   - `delegate.key` (`xonly_64hex`) signs child grants ONLY (disjoint from issuer, recipient, and messaging keys; held in an isolated delegation signing service enforcing at-most-one signature per row, `guides/GUIDE-01-custody-and-signers.md`).
   - `delegate.child_seal_key` (`compressed_66hex`) controls the issuer revocation branch of every child grant's seal (held outside the delegation signer so the delegator can revoke children even if the delegation signer is compromised).
2. **Grouped rows, row coins, and pairwise disjointness (`R8.6`):**
   - `delegate.groups` holds `1..16` groups; each group pairs a `template` (concrete `executor`, closed `recipient_rule` (`exact_key | exact_name | member_class`), `capabilities[]`, and `notary_mode`) with `1..16` `ranges` of `1..2048` pre-confirmed P2WPKH row coins (`first_vout + count <= 2^32`, confirmed `<= parent.recent_block`).
   - **Disjoint coin ranges (`R8.6`):** Every `(txid, vout)` across ALL row ranges and ALL stop-coin ranges across ALL groups in `delegate.groups`, as well as the parent's own `seal` and linkage output, MUST be pairwise disjoint (`GRANT_ROW_INVALID`).
   - Global 1-based `ordinal` enumerates rows in signed group/range order. A child naming `parent: {grant_id, ordinal}` MUST have its individual `0x01` issuance anchor (never `0x02`) spend the exact row coin for `ordinal` (`GRANT_ROW_INVALID`), enforcing on chain that at most one child per row exists.
3. **Whole-parent aggregate budget (`R8.5`) and mechanical child narrowing (`SL-GRNT-010`, `decided`):**
   Every verifier MUST check BOTH the whole parent allocation AND the individual child:
   - **Whole-parent budget sum (`R8.5`):** For every quota key `q = (kind, resource, unit, window)` appearing in any group template's `capabilities[].quotas`, let `rows(g) = sum(r.count for r in g.ranges)` and `cap(g, q)` be the maximum ceiling for `q` in group `g`'s template (summed across capabilities in `g` that share `q`). Using exact integer arithmetic (overflow -> `GRANT_CHILD_WIDER`), the verifier MUST confirm a matching pool entry `pool_max(q)` exists in `delegate.pools`, that `pool_max(q) <= root_cap(q)` whenever the parent root grant itself carries a matching quota `q`, and that:
     ```text
     sum over all groups g of (rows(g) * cap(g, q)) <= pool_max(q)
     ```
     Failure refuses `GRANT_CHILD_WIDER`. *(This invariant prevents sibling rows at different executors from exceeding the parent's total budget.)*
   - **Child-within-parent check:**
     - `C.genesis == P.genesis`, `C.contract_id == P.contract_id` (if present), `C.executor == template.executor`, and `C.revocation.mode == "seal"` with issuer branch controlled by `P.delegate.child_seal_key`;
     - `[C.not_before_height, C.not_after_height) ⊆ [P.not_before_height, P.not_after_height)`;
     - Every capability in `C.capabilities` mechanically narrows a capability in `template.capabilities` under the 7-predicate Constraint Algebra (`SL-WIRE-017`), and every child quota `<=` the template's row cap;
     - `C.recipient` satisfies `template.recipient_rule` (`exact_key` matches `mode="key"` with exact `pk`; `exact_name` matches `mode="name"` with equal `(name, registration, owner_policy)`; `member_class` checks live unspent membership of `C.recipient`'s `(name, registration, owner_policy)` with unspent member `seal` in at least one pinned operator's confirmed `seallink-members-list/1`).
4. **Optional notary and stop coins (`SL-GRNT-011`, `decided`):**
   - `"none"` (default): mechanical narrowing under `SL-GRNT-010` requires no notary.
   - `"optional_stop"`: range specifies confirmed P2WPKH stop coins controlled by a pinned notary (`notary_name` + `notaries[]`); spending a stop coin permanently closes that row for cause across all verifiers (`GRANT_ROW_STOPPED`).
   - `"required_act"`: additionally requires a verified `seallink-notary/1` (`act_kind = "child-within-parent"`, exact `(parent_grant_id, child_grant_id, ordinal)` and pinned notary verification per `SPEC-05 §5`, `NOTARY_REQUIRED`).

## 4. Deterministic Admission Order (Invocation Pipeline)

An executor MUST evaluate an incoming `seallink-invocation/1` in this exact 12-step order, returning the **first** failure (`SL-GRNT-012`, `decided`). Early recipient authentication runs strictly **before** cached-receipt lookup and blockchain RPCs to prevent unauthenticated DoS, cached-receipt harvesting, and state-oracle leakage:

1. **Invocation wire check (`SPEC-01 §7`):** Parse and verify `seallink-invocation/1` syntax, JCS, closed schema, profile argument schema, keys, and self-consistent `SignatureSet` -> `WIRE_*`
2. **Early local request checks (pre-chain):**
   - 2a. Wall-clock half-open window `iat <= now < exp` -> `INVOKE_TIME_INVALID`
   - 2b. `invocation.executor` equals this executor's pinned `(name, receipt_key)` -> `GRANT_EXECUTOR_MISMATCH`
3. **Presented bundle wire, early recipient authentication, and replay check (pre-chain):**
   - 3a. Wire pipeline on presented grant(s), optional contract(s), and optional manifest(s) -> `WIRE_*`
   - 3b. If leaf grant uses `recipient.mode = "key"` or `"group"`, verify `invocation.signatures.policy` equals `grant.recipient` immediately -> `WIRE_SIGNATURE` *(runs before any cached-receipt lookup so forged callers cannot probe or retrieve cached receipts)*
   - 3c. For `key` and `group` recipients (whose authentication succeeded in Step 3b): check local journal replay/nonce table. If `invocation_id` already has a stored terminal receipt, return that cached receipt (or `INVOKE_REPLAY` if profile forbids cached return). If `invocation_id` has an unsettled `reservation` (crash inside the external-effect window before receipt persistence), return `outcome = "uncertain"` while retaining the reservation and executing zero second effect. If `nonce` was already used for a different `invocation_id`, refuse `INVOKE_REPLAY`. *(For `recipient.mode = "name"`, this identical replay/crash-recovery check runs immediately after Step 11a once the recipient's on-chain key is verified.)*
4. **Consistent chain observation (`SPEC-02 §4`):** Check in strict order:
   - 4a. Snapshot tip bracket `(hash_0, height_0) == (hash_1, height_1)` -> `CHAIN_OBSERVATION_VOID` *(checked BEFORE comparison peers)*
   - 4b. Chain/genesis pin -> `CHAIN_MISMATCH`
   - 4c. Reading node health (`!IBD`, `txindex=1`, header lag `<= LAG`) -> `CHAIN_UNHEALTHY`
   - 4d. Independent comparison peer veto (`>= 1` healthy peer required -> `CHAIN_UNHEALTHY`; disagreement -> `CHAIN_NODE_DISAGREEMENT`)
   - 4e. Monotonic UTC clock watermark and header future bound `S` -> `CHAIN_CLOCK_ERROR`
   - 4f. Action risk-class tip freshness (`tip_age`) -> `CHAIN_TIP_STALE`
5. **Journal continuity (`§6`):** Check external CAS witness readability, local store readability, and `journal_id` match (`JOURNAL_LOST`), then active `write_token` (`JOURNAL_FENCED`), then position/commitment continuity (`JOURNAL_LOST`)
6. **Durable closure check:** Check local closure journal for every grant ID, contract ID, framework ID, credential ID, origin ID, guardian slot, issuer role, seal, and row in `proof_path`, in strict order:
   - 6a. Closed grant or ancestor grant -> `INVOKE_REPLAY` if closed specifically by `SINGLE_USE_CONSUMED` (for a new `invocation_id`), else `GRANT_CLOSED`
   - 6b. Stopped row -> `GRANT_ROW_STOPPED`
   - 6c. Closed issuer role (strictly keyed by `(cause, name, registration, role, policy_sha256)` — checking `CRED_ISSUER_CLOSED` against `cutoff_height` **strictly before** `NAME_ROLE_CHANGED` against `retired_before_height` so `0x0b` compromise ALWAYS takes precedence over routine rotation, including across `A -> B -> A` returns on both stateful and fresh verifiers) -> `CRED_ISSUER_CLOSED` / `NAME_ROLE_CHANGED`
   - 6d. Closed contract, framework, credential, origin, guardian slot, or seal -> `SEAL_SPENT` / `SUBJECT_ENDED` / `GUARDIAN_INACTIVE`
7. **Issuer identity, origin, and guardianship (`SPEC-03`, `SPEC-04`):**
   - 7a. Resolve root issuer name (`NAME_NOT_FOUND`), liveness (`NAME_EXPIRED`), history walk availability (`NAME_HISTORY_UNAVAILABLE`), `SIGHASH_ALL` writer check (`NAME_WRITER_UNVERIFIED`), `owner_policy` match (`NAME_OWNER_MISMATCH`), 520B name value grammar (`NAME_VALUE_INVALID`). For autonomous issuers (including State-4 emancipated origins, where the active authorized policy is `effective_binding.owner_policy`): check `link.grant` continuity (`NAME_ROLE_CHANGED`) — **BEFORE writing a durable policy-scoped `NAME_ROLE_CHANGED` closure to `FencedJournal`, verifiers MUST authenticate `root_grant`'s signature against the historical `link.grant` policy active at `recent_block`** (so forged unauthenticated grants refuse `WIRE_SIGNATURE` with **zero** closures written, while authentic retired grants close strictly `policy_sha256(retired_policy)` leaving successor `link.grant` policies unaffected in the same journal) — verify live `0x0b` compromise status (`CRED_ISSUER_CLOSED`), and verify `issuer.role_policy` matches `link.grant` and equals `root_grant.signatures.policy` (`WIRE_SIGNATURE`).
   - 7b. Perform history- and binding-based origin detection across the issuer's full confirmed update chain (`SL-ORIG-003`). If origin-certified (confirmed `link.origin` in history OR confirmed `0x0c` binding OR pinned origin): verify `origin_bundle`'s active `NameBinding` (or `effective_binding` in State 4) matches `root_grant.issuer` and `origin_id == link.origin`, then check in strict order: `origin/1` validity & trust (`ORIGIN_UNVERIFIED`), `name-binding/1` validity (`ORIGIN_BINDING_INVALID`), `status_seal` and `roster_seal` completeness (`ORIGIN_STATUS_INCOMPLETE`), subject end (`SUBJECT_ENDED`), pending emancipation transfer (`GUARDIAN_TRANSFER_PENDING`), calendar majority time boundary (`GUARDIAN_TIME_BOUNDARY`); if `ward`, enforce `SL-ORIG-006` two-pass order (`WARD_AUTONOMOUS_FORBIDDEN`, `ORIGIN_UNVERIFIED`, `GUARDIAN_QUORUM_UNMET` [revision], `GUARDIAN_INACTIVE` [all slots], `WIRE_SIGNATURE`, `GUARDIAN_QUORUM_UNMET` [event_class/count]).
8. **Contract and framework checks (`SPEC-05`):** Check in strict order: action requires contract (`GRANT_CONTRACT_REQUIRED`); if `contract_id` present: presentation (`CONTRACT_NOT_PRESENTED`), ID recomputation (`CONTRACT_ID_MISMATCH`), persisted `contract`/`framework` closure (`SEAL_SPENT`), party assents (`CONTRACT_ASSENT_INVALID`, incl. multi-ward bundles verified at confirmed `h_anchor` & anchor-time `issued_at <= anchor_time < expires_at` 72h freshness with no wall-clock fallback), confirmed seal presence & `ContractSealScriptPolicy` match (`CONTRACT_SEAL_MISSING`), seal spend (`SEAL_SPENT`) or inconclusive seal (`SEAL_UNAVAILABLE`), disclosed `machine_clause_indices` (`ClauseObject`/`MachineClauseTerms`) narrowing, distinct party identities & grant-participant binding, & window/calendar nesting (`CONTRACT_TERMS_MISMATCH` / `GRANT_WINDOW_CLOSED`), runtime `config_sha256` if required (`CONTRACT_CONFIG_MISMATCH`).
9. **Re-delegation checks (depth 2, `§3`):** Check in strict order: parent delegation rights & depth `<= 2` (`GRANT_NOT_DELEGABLE`), whole-parent R8.5 aggregate pool sum & `pool <= root` (`GRANT_CHILD_WIDER`), R8.6 disjointness & ordinal row coin spend on `0x01` alongside child's own `(child_seal_txid, child_seal_vout + 1)` — failing closed with `GRANT_ROW_INVALID` whenever `row_cre_tx` is absent from `ChainView` or does not match the compiled P2WPKH row coin script (`GRANT_ROW_INVALID` / `CHAIN_TX_CONSTRUCTION`), stop coin live failing closed if missing/unconfirmed/wrong script (`SEAL_UNAVAILABLE` / `GRANT_ROW_STOPPED`), optional notary act (`NOTARY_REQUIRED`), child `signatures.policy` equals `parent.delegate.key` (`WIRE_SIGNATURE`), mechanical child narrowing & `recipient_rule` against group template (`GRANT_CHILD_WIDER`).
10. **Grant window, revocation / single-use seal, and executor binding:**
    - 10a. Grant height window `[not_before_height, not_after_height)` AND `not_after_height <= issuer_name_expiry_at_issuance` -> `GRANT_WINDOW_CLOSED`
    - 10b. If `revocation.mode = "window_only"`: enforce `not_after_height - not_before_height <= 12` (`WIRE_INTEGER`), then executor opt-in policy (`GRANT_SEAL_REQUIRED`)
    - 10c. If `revocation.mode = "seal"`: verify issuance `0x01`/`0x02` frame (`0x01` mandatory for children), exact `seallink-issuance/1` preimage & Merkle proof (`CHAIN_FRAME_INVALID`), `recent_block` recency (`CHAIN_RECENCY_INVALID`), Witness `W` construction & exact `(seal_txid, seal_vout + 1)` linkage on BOTH root and child grants plus confirmed funding inputs `< anchor_height` (`CHAIN_TX_CONSTRUCTION`), anchor depth (`CHAIN_DEPTH_INSUFFICIENT`); then evaluate seal:
      - `revocable` (`SPEC-02 §6.1`): `revoked` -> write closure + `SEAL_SPENT`; `unavailable` -> `SEAL_UNAVAILABLE`
      - `single_use` (`SPEC-02 §6.2`): `awaiting_spend` -> `SEAL_UNAVAILABLE`; `revoked` -> write closure + `SEAL_SPENT` (except foreign `0x11` anti-DoS which refuses `SEAL_SPENT` without writing closure); `pending_confirm` -> `CHAIN_DEPTH_INSUFFICIENT`; `consumed` with distinct `invocation_id` -> `INVOKE_REPLAY`
    - 10d. Verify `executor` or resolve `executor_ref`: forbid `executor_ref` if the grant includes `delegate`, uses `single_use`, carries any `quotas`, or declares any capability in `grant.capabilities[]` with `external_mutation = true` or `allows_executor_ref = false` (`GRANT_EXECUTOR_REF_FORBIDDEN`; evaluated strictly against `grant.capabilities[]` so unauthorized `invocation.action` values reach Step 11b `INVOKE_ACTION_DENIED`); require `executor_ref.provider_of == root_grant.issuer.name` (`GRANT_TARGET_UNAUTHORIZED`); verify holder's confirmed manifest (`MANIFEST_UNAVAILABLE`, then `MANIFEST_MISMATCH`, then `MANIFEST_ROLLBACK`), confirm provider `NamePin` binding (`SERVICE_PROVIDER_UNBOUND`) and provider `owner_policy` (`NAME_OWNER_MISMATCH`), confirm resolved `(name, receipt_key)` matches this executor (`GRANT_EXECUTOR_MISMATCH`)
11. **Named recipient, action, text ban, target authority, and constraints:**
    - 11a. If leaf grant uses `recipient.mode = "name"`, resolve recipient name (`NAME_NOT_FOUND`), check liveness (`NAME_EXPIRED`), verify active `registration` and `owner_policy` with writer-verified history (`NAME_OWNER_MISMATCH`), verify `invocation.signatures.policy` against its authorized request key (`WIRE_SIGNATURE`), and then execute the Step 3c local journal replay / crash-recovery check (`INVOKE_REPLAY`, cached receipt, or `uncertain`)
    - 11b. Action registered in `registry/actions.json` (or explicit local extension config), supported by this executor, and present in `grant.capabilities` (`INVOKE_ACTION_DENIED`)
    - 11c. Mechanical effect text ban (`GRANT_TEXT_FORBIDDEN`)
    - 11d. **Target authority verification (fail-closed):** Validate `invocation.target` syntax (`registry/actions.json`) and confirm the root grant's issuer has authority over the target resource:
      - `mailbox:<owner>:<label>`: `root.issuer.name == <owner>` (`GRANT_TARGET_UNAUTHORIZED` otherwise) AND `<owner>`'s confirmed `seallink-manifest/1` binds this executor's exact `NamePin` for `("mail", <label>)` — **mandatory for BOTH `executor_ref` AND concrete `executor` grants** (`SERVICE_PROVIDER_UNBOUND` if missing or mismatched);
      - `station:<host>:<slot>`: `<host> == executor.name` AND the root issuer's complete `NamePin` is authorized EITHER in the host's explicit local `station_slot_bindings[target]` allowlist OR (when `executor_cfg.pin` is configured with matching `NamePin`, or explicit `self_hosted: true` for `<host> == executor.name`) equals the verified `<host>` owner `NamePin` itself (fail-closed default: any other issuer refuses `GRANT_TARGET_UNAUTHORIZED`);
      - `ward:<origin_id>`: `origin_id == pinned_ward_origin_id` and valid ward grant for `origin_id` (`GRANT_TARGET_UNAUTHORIZED` otherwise).
    - 11e. Target match against `grant.capabilities[].target`, profile-specific server-side checks (`mail/read` `where` constraints on `folder`, `sender_domain`, and `max_bytes` MUST ALL evaluate against server-observed `actual_message_meta` — omitting `actual_message_meta` when any such constraint is declared refuses `INVOKE_CONSTRAINT_FAILED`; `agent/guardian-message` `raw_message_bytes` & `subject_ward_name`), and 7-predicate `where` evaluation against `invocation.arguments` (`INVOKE_CONSTRAINT_FAILED`)
12. **Pre-effect recheck and atomic Phase 1 reservation (`admit_and_reserve`):** Execute closed-bracket `pre_effect_recheck` (`SPEC-02 §4` -> `CHAIN_OBSERVATION_VOID`, `CHAIN_UNHEALTHY`, `CHAIN_NODE_DISAGREEMENT`, `CHAIN_CLOCK_ERROR`, `CHAIN_TIP_STALE`, `INVOKE_TIME_INVALID`, `SEAL_SPENT`, `NAME_ROLE_CHANGED`), verify required quota presence with exact `resource == target` and seconds-window monotonic clock (`QUOTA_CLOCK_REGRESSION`), and append ONE single atomic `reservation` journal entry carrying `nonce` + `reservations[]` (`QUOTA_EXCEEDED`, then `JOURNAL_FENCED`, then `JOURNAL_LOST`). Upon effect completion, Phase 2 (`commit_result`) verifies and reconciles the signed receipt 1-to-1 against the reservation, persists the verified receipt blob FIRST, and appends ONE atomic terminal `settlement` entry (`§2.2`).

## 5. Bearer Sessions for Non-Signing Clients (`seallink-session-open/1`)

When a client harness cannot sign per-request invocations (e.g., an SDK accepting only a base URL and bearer token), an executor MAY declare conformance to the optional v1.0 **Bearer Sessions** module (`CONFORMANCE.md §1.1`) (`SL-GRNT-013`, `decided`). Executors that do NOT declare this module MUST refuse `seallink-session-open/1` and bearer-session calls fail-closed with **`ACTION_UNSUPPORTED`** and zero journal writes.

1. **Session lifecycle (`seallink-session-open/1`, `<= 16384` bytes, `op = "open" | "extend" | "close"`):**
   - **`op = "open"`:** Recipient's key holder sends a signed `seallink-session-open/1` (omitting `session_id`) specifying `slot_binding`, bounded `quotas` (every quota ceiling MUST be `<=` the backing grant's matching quota, AND every `required_quotas` entry declared in `registry/actions.json` for any capability in the backing grant MUST be present on both the capability and the session with exact `resource == target` -> `QUOTA_EXCEEDED`), and `exp <= now + 3600` (at most 1 hour ahead). Executor MUST run the **complete `§4` backing-grant chain admission** (verifying chain observation, journal continuity, durable closures, issuer identity/origin/guardianship, contracts including `config_sha256` / `runtime_config_sha256` -> `CONTRACT_CONFIG_MISMATCH`, depth-2 delegation if applicable, window, live seal, executor binding, recipient authority, and target authority; forbidding `single_use`, `window_only`, and any action with `allows_bearer_session = false` in `registry/actions.json` -> `SESSION_INVALID`), mint a fresh `session_id` and a **32-byte CSPRNG bearer token encoded as strictly 64 lowercase hexadecimal ASCII characters (`token`, matching `^[0-9a-f]{64}$`)** (`>= 256` bits of entropy, NEVER derived from deterministic public fields; non-conforming caller-injected tokens refuse `SESSION_INVALID`), persist ONE atomic `session-state` `JournalEntry` recording `(session_id, state = "open", grant_id, token_sha256 = SHA256(UTF8(token)), nonce, exp, slot_binding, session_quotas, proof_path?, root_recent_height?)` (recording `root_recent_height = root_grant.recent_block.height` so `use` enforces exact epoch-scoped `NAME_ROLE_CHANGED` and `0x0b` checks across restarts), and return `bearer_token = token` once in the `open` response over a local socket or mutually authenticated encrypted channel.
   - **`op = "extend"`:** Requires `session_id` referencing an existing `"open"` session with matching `grant_id` and `slot_binding` signed by the recipient; re-runs full live `§4` backing-grant chain verification, requires `new_exp <= now + 3600` and **strictly non-widening** `quotas` (`new_max <= prev_max` for every existing session quota key and no widened ceilings -> `SESSION_INVALID`), and appends an updated `session-state` entry to `FencedJournal`.
   - **`op = "close"`:** Requires `session_id` with matching `grant_id` and `slot_binding`; MAY be signed by **either** the backing grant's recipient OR an autonomous root grant issuer (`link.grant`), immediately appending `session-state` (`state = "closed"`) to `FencedJournal`; all subsequent requests using that token refuse `SESSION_INVALID`. *(Ward issuers do not sign `seallink-session-open/1` directly because `SessionOpen` carries `signatures` only; a ward's guardians immediately close any active bearer session by spending the backing grant's revocation seal (`SEAL_SPENT`), or the recipient sends `op = "close"`.)*
2. **Per-use in-session verification & durable atomic `session-use` debits:** For **every** unsigned in-session request presenting `token` (strictly 64 lowercase hex ASCII characters, else `SESSION_INVALID`) plus mandatory `(action, target, arguments)` (missing or non-string `action`/`target`, non-object `arguments`, or `allows_bearer_session = false` refuses **`SESSION_INVALID`**), the executor selects chain freshness `risk_class` from `registry/actions.json` for the requested `action` (Class 1 `3600s` for `mail/send`, `agent/tool`, `agent/session`; Class 2 `5400s` for `mail/read`, `mail/list`), runs `check_chain_observation(chain, risk_class)`, computes `SHA256(UTF8(token))` (constant-time comparison against journaled `token_sha256`), verifies `state == "open"` and `now < exp` (`SESSION_INVALID`), and **MUST re-run live `§4` backing-grant verification** against the current `grant_env` — NEVER trusting cached session state alone:
   - Re-resolve root issuer `link.grant` using exact `root_recent_height` (from `root_grant.recent_block.height` / journaled `root_recent_height`; missing `recent_block` fails closed `SESSION_INVALID`), verify cause-/epoch-scoped role closures (`CRED_ISSUER_CLOSED` before `NAME_ROLE_CHANGED`) and live `0x0b` break, and re-verify active origin/ward status (requiring `origin_bundle` whenever the root issuer is origin-certified);
   - Verify live backing grant revocation seal (forbidding `single_use`, checking durable `grant` and `seal` closures at `required_depth = max(grant.min_depth, operator_min_depth)`), height window, AND (when `proof_path` was persisted in `session-state` at `open`) re-verify the active-chain `0x01`/`0x02` issuance anchor (including `batch_proof` for `0x02`), `recent_block` recency, and confirmation depth against reorgs; for depth-2 child backing grants, require `parent_grant_env` (`SESSION_INVALID` if omitted), verify parent live seal, height window, active-chain anchor (when persisted), and live `stop_outpoint` (recording durable `GRANT_ROW_STOPPED` closure and returning external `SESSION_INVALID` if spent), and anchor `row` block buckets strictly at `parent.not_before_height`;
   - Whenever `contract_id` is present on the backing grant, **require** `contract_env` (`SESSION_INVALID` if omitted), verify live `contract_seal`, contract height/calendar window, disclosed `machine_clause_indices` (when present), AND `runtime_config_sha256 == contract.config_sha256` (when `contract.config_sha256` or `executor_cfg.runtime_config_sha256` is configured -> `CONTRACT_CONFIG_MISMATCH`); whenever `contract.framework_id` is present **require** `framework_contract_env` (`SESSION_INVALID` if omitted) and live framework seal & window;
   - Re-verify `executor_ref` (if backing grant uses `executor_ref`) against `executor_cfg` and holder's confirmed manifest; validate `arguments` against the owning profile's closed argument schema (`WIRE_MEMBER`), match `(action, target)` against a capability in `grant.capabilities[]`, enforce ALL `where` predicates including server-observed `mail/read` `actual_message_meta` (`INVOKE_CONSTRAINT_FAILED`), AND verify EVERY `required_quotas` entry from `registry/actions.json` for `action` is present on BOTH the matched capability and `session.quotas` with exact `resource == target` (`QUOTA_EXCEEDED`).
   It then atomically debits **ONLY the `session.quotas` entries belonging to the matched capability** (leaving unrelated capabilities' session quotas untouched) in deterministic per-quota `session -> own -> [row]` order by appending ONE durable **`session-use`** `JournalEntry` (`debits.maxItems = 96`, supporting all 32 capability quotas across all 3 accounts) so all three accounts survive crash and restart replay (`QUOTA_EXCEEDED` on overrun).
3. **Honest boundary:** Unsigned in-session requests lack per-request non-repudiation and retry idempotency; executors MUST NOT enable bearer sessions for wallets, name updates, or irreversible financial transfers.

## 6. Anti-Rollback Fenced Journals (`seallink-journal-entry/1`)

Every stateful SealLink verifier/executor (tracking closures, single-use consumption, quota reservations, nonces, bearer sessions, migrations, and manifest heads) MUST guard against backup-restore and equal-position forks using a hash-chained journal + external CAS witness (`SL-GRNT-014`, `decided` state machine / `open` witness wire transport in `OPEN-QUESTIONS.md`):

1. **Hash chain & strict wire enforcement (`65536` B ceiling):** Random 32-byte `journal_id`; commitment `c(0) = H_tag("seallink-journal/1", journal_id)`, `c(n) = H_tag("seallink-journal/1", c(n-1) || canonical_JCS(entry_n))`. Every `entry_n` MUST pass full `SPEC-01 §7` wire validation (including the `65536`-byte ceiling of `seallink-journal-entry/1` and closed Draft 2020-12 `JournalEntry` schema in `schemas/invocation.schema.json`) **BOTH before appending/mutating state AND on every replayed entry** (`WIRE_SIZE` / `WIRE_*` on violation), with `entry_n.pos == n` and `entry_n.prev_commitment == c(n-1)`. Every `closure` entry carries a discriminated `ClosureSubject` covering ALL 8 `creates_closure = true` refusal codes (`GRANT_CLOSED`, `GRANT_ROW_STOPPED`, `NAME_ROLE_CHANGED`, `SEAL_SPENT`, `CRED_ISSUER_CLOSED`, `CRED_REVOKED_FOR_CAUSE`, `SUBJECT_ENDED`, `NOTARY_LOG_COMPROMISED`). `manifest-head` entries persist per-set `(seq, sha256)` watermarks (`sets`) and durable `removed_sets` marks (`SL-IDEN-008`, surviving reorgs). Confirmed `0x14` transparency/denial log heads are persisted as `JournalEntry(kind = "log-head")` (including `handover_next_outpoint` / `handover_next_policy` on `O(1)` handover terminals) strictly after reaching `required_depth` (never mutated by provisional gossip revocations).
2. **External witness & CAS writer fencing:** An append-only CAS register stored strictly outside the local store's backup domain, holding `(journal_id, pos, commitment, write_token)`. Only `advance(journal_id, token, pos, from_commit, to_commit)` mutates it; fencing strictly increments `write_token`. Every `append` MUST perform an atomic CAS check against the external witness `(write_token, expected_head_pos)` and refuse **`JOURNAL_FENCED`** if another replica holds a newer `write_token` or advanced the head concurrently.
3. **Write order:** Check continuity -> validate wire bytes -> durably write local entry -> CAS `advance` external witness -> execute effect.
4. **Continuity precedence:** (1) witness readable, (2) local store readable, (3) matching `journal_id` -> else `JOURNAL_LOST`; (4) active `write_token` held -> else `JOURNAL_FENCED` (checked before position comparison so partitioned replicas fence cleanly); (5) `store.pos == witness.pos` and equal commitment (`Intact`), or `store.pos == witness.pos + 1` with matching `prev_commitment` (`Pending` completion), else `JOURNAL_LOST`.
5. **Attended recovery (start anew):** Record `recovery` entry with `fenced_at`, wait for a confirmed ledger block `boundary` whose `header_time > fenced_at + 7200s` (exceeding Namecoin's +2h future-header consensus bound to prove the block was accepted after fencing), and conservatively treat all pre-fencing uncertain reservations as consumed.
6. **Witness-verified restart reconstruction (mandatory by default):** On restart, `replay_persisted_entries` MUST verify the replayed local entries against the external CAS witness `(witness_pos, witness_commitment, write_token)` by default (`require_witness = true`; missing witness head MUST fail closed with `JOURNAL_LOST`, and any divergence MUST return `JOURNAL_FENCED` or `JOURNAL_LOST` — NEVER silently accepting an unverified log or crashing on assertions). Every replayed entry is wire- and schema-validated before mutating reconstructed state. Replay MUST deterministically restore: (a) the hash-chain commitment, closures across ALL `ClosureSubject` kinds, nonces, open bearer sessions (including `token_sha256` & `nonce`), applied migrations, and per-account (`own`, per-`row_ordinal` `row`, `session`) quota balances (including `session-use` debits); (b) unsettled `reservation` entries as `uncertain` invocations; (c) monotonic per-quota clock watermarks (`quota_watermarks[qkey] = max(recorded_at)`) for every `seconds:*` window so post-restart clock rollbacks refuse `QUOTA_CLOCK_REGRESSION`; and (d) the idempotent cached receipt index (`invocation_id -> receipt`) AND `single_use_consumed` state by resolving `settlement.receipt_sha256` (including unified `settlement` entries with `single_use_consumed: true`) against the durable content-addressed receipt store (verifying `content_addr(blob) == receipt_sha256`, and refusing `INVOKE_REPLAY` if a terminal entry's receipt blob is missing or corrupt — NEVER re-executing).

## 7. Security Considerations

- **No cross-executor quota sharing:** Two independent executors MUST NEVER spend from one apparent grant quota; split budgets across separate concrete-executor grants or parent row groups verified under R8.5.
- **Closure write failure:** If writing a newly observed `SEAL_SPENT` closure to the journal fails, the verifier MUST refuse admission and halt further admission for that seal until durable storage recovers.
- **`window_only` containment:** Executors opting into root `window_only` MUST enforce low per-grant and global operator ceilings so a compromised `grant` key's damage is bounded even before an emergency name update propagates.
